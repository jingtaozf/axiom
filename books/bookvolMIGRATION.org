#+BEGIN_abstract
This book documents the migration of Tim Daly's literate Axiom (the
``30 Year Horizon'' code base) from its historical AKCL/GCL host Lisp to
a modern ANSI Common Lisp, Steel Bank Common Lisp (SBCL), so that
*AXIOMsys* can be built and used on contemporary platforms,
including Apple Silicon macOS.

The migration is conducted as literate programming. Per the project's
Rule~0, the document is the deliverable and the code is a by-product the
document generates. The reader who finishes this book should understand
/why/ Axiom is bound to GCL, /where/ that binding lives, and
/how/ each binding is replaced --- before a single line of new Lisp
is compiled. The companion fork OpenAxiom, which already performed an
equivalent port, is used throughout as a behavioural /oracle/: we
read it to learn the per-Lisp semantics, then re-author that knowledge
here in Axiom's own pamphlet style. We never copy OpenAxiom sources or
its directory layout into this tree.
#+END_abstract


\section{Why this book exists}

Three forks descend from the 1992 Axiom: Tim Daly's *Axiom*
(this repository), *FriCAS*, and *OpenAxiom*. FriCAS and
OpenAxiom are actively buildable on modern multi-Lisp toolchains, but in
gaining that portability they moved away from Axiom's original literate
form: FriCAS keeps only an optional weak literate convention, and
OpenAxiom, while it retains literate =.spad.pamphlet= algebra,
reorganised the host layer into a plain =src/lisp/= directory.

We deliberately chose =daly/axiom= instead, precisely because it
is the /most/ literate of the family --- every source file is
embedded in a pamphlet, every directory carries a
=Makefile.pamphlet=, and the documentation is primary. Our goal
is not merely a running binary; it is to /learn the classic system/
by carrying its literate discipline through a real port. If we wanted
only a working computer-algebra system on macOS we would install FriCAS
in five minutes. We want the understanding, written down.

Therefore this book is mostly prose. Code chunks appear only where a
concrete snippet teaches something the prose cannot, and each is
preceded by the reasoning that motivates it.

\section{What binds Axiom to GCL}

Axiom does not ``prefer'' GCL; its entire build architecture is welded to
the AKCL/GCL family. Five distinct couplings, found by inspecting this
repository, must each be understood before they can be replaced.

\subsection{The image-dump architecture}

Axiom is built by loading every compiled file into a running Lisp and
then dumping the live memory image to disk as the *AXIOMsys*
executable. The dump is performed by the GCL primitive
=system::save-system=. In this repository the call lives in
=books/bookvol5.pamphlet= inside the chunk =spad-save=,
annotated with the cross references
=\\calls\{spad-save\}\{save-system\}= and
=\\usesdollar\{spad-save\}\{SpadServer\}=. The relevant fragment
is conditionalised per host:

\begin{verbatim}
(defun user::spad-save (save-file)
  ...
  #+:AKCL   (system::save-system save-file)
  #+:allegro (excl::dumplisp :name save-file ...)
  #+Lucid   ...)
\end{verbatim}

There is no =#+:sbcl= branch. This single fact is the heart of
the port: without an SBCL arm here, the system cannot produce its
executable image at all. The ANSI-era replacement is
=sb-ext:save-lisp-and-die=, which both writes a standalone
executable and folds in the entry point. See the oracle reference in
Section~[[#sec:oracle][sec:oracle]].

\subsection{The VMLISP portability layer}

Axiom is not written directly against ANSI Common Lisp. It is written
against *VMLISP*, a portability layer inherited from the
Scratchpad and Lisp-Machine era, referenced over five hundred times
across the interpreter sources. VMLISP is the real ``language'' the
interpreter speaks; the host Lisp only needs to provide a handful of
primitives underneath it --- image save, garbage collection, environment
access, and a foreign-function interface. Most of the port's surface
area is making VMLISP rest on SBCL instead of on GCL internals.

\subsection{The GCL foreign-function interface}

Axiom reaches into C through GCL's =defentry= and =clines=
mechanisms. Twenty-three =defentry= bindings exist; by inspection
they fall into four groups: sockets for the HyperDoc and graphics
client/server (=sock\_send\_int=, =open\_server=,
=server\_switch=, and siblings), hashing
(=hashString=, =hashCombine=), floating-point edge values
(=NANQ=, =plus\_infinity=, =minus\_infinity=), and
filesystem predicates (=directoryp=, =writeablep=). SBCL
expresses the same bindings through =sb-alien= (or CFFI). For a
/core/ computer-algebra system, only the hash, float, and
filesystem entries are essential; the socket group belongs to HyperDoc
and may be stubbed initially (Section~[[#sec:plan][sec:plan]]).

\subsection{GCL internal packages}

The interpreter calls directly into GCL's private packages:
=si::= (system internals), =system::=, and
=compiler::=. Each such call must be mapped to its SBCL
equivalent or routed through a new shim in the VMLISP layer.

\subsection{A bundled, self-compiled GCL}

Finally, GCL is not even an external dependency here: the build patches
and compiles a specific GCL from source. The selected version is set in
the top =Makefile= (=GCLVERSION=gcl-2.6.13pre=), and the
=zips/= directory carries dozens of version-specific GCL patches.
Part of the port is simply deleting this self-compiled-GCL machinery and
pointing the build at a system SBCL.

\section{The bootstrap chain (Stage 1)}

To know where the couplings of the previous section actually fire, one
must follow how Axiom builds itself. The chain has three images, each
built from the previous:

- *bootsys* --- the bootstrap of the BOOT translator. BOOT is
  Axiom's implementation language; it is translated down to Lisp. The
  BOOT-to-Lisp translator must itself run on the host Lisp.
- *interpsys* --- the interpreter image, built by loading the
  translated interpreter sources into the host Lisp.
- *AXIOMsys* --- the final executable, produced when
  =spad-save= dumps the populated interpreter image
  (Section~2.1).


The host Lisp is touched at every hop: the translator runs on it, the
interpreter is loaded into it, and the final image is dumped by its
=save-system= primitive. A subtle consequence is that Axiom's own
/tangle/ step is performed by a Lisp function inside the image
(=LISPTANGLE= resolves to =bin/lisp=), so the tangler and
the host Lisp are entangled at bootstrap. Mapping each hop onto SBCL is
the substance of Stage~5 in the plan below.

\section{The OpenAxiom oracle}
# label: sec:oracle

OpenAxiom already carried this code base onto SBCL, CLISP, ECL and
Clozure. We use it strictly as a reference. The decisive artefact is its
host-abstraction file =src/lisp/core.lisp.in=, whose
=saveCore= function is the multi-Lisp generalisation of Axiom's
=spad-save=:

\begin{verbatim}
;; open-axiom src/lisp/core.lisp.in  (READ-ONLY oracle, not copied)
(defun |saveCore| (core-image &optional (entry-point nil))
  #+:sbcl    (sb-ext:save-lisp-and-die core-image
                                       :toplevel entry-point :executable t)
  #+:gcl     (system::save-system core-image)
  #+:clisp   (ext::saveinitmem core-image :init-function entry-point ...)
  #+:clozure (ccl:save-application core-image
                                   :toplevel-function entry-point ...))
\end{verbatim}

The lesson we extract --- and re-author in Axiom's style when we reach
Stage~2 --- is the SBCL arm and the entry-point handling. We do
/not/ import this file, its =src/lisp/= layout, or
OpenAxiom's autoconf/CMake build. The SBCL branch will instead be added,
as literate prose plus a =\\begin\{chunk\}=, to the existing
=spad-save= chapter and a new portability chapter within Axiom's
book structure.

That OpenAxiom builds and runs on our target platform is not assumed; it
was demonstrated. On an Apple Silicon Mac (=arm-apple-darwin=)
with SBCL, a full build produced 1196 compiled algebra libraries and a
working interpreter; =integrate(1/(x\^{}3+1), x)= returned the
correct closed form involving a logarithmic and an arctangent term. This
gives us a behavioural oracle to compare Axiom's ported output against,
domain by domain.

\section{The migration plan}
# label: sec:plan

The guiding principle is /graft, do not rewrite/. The SPAD algebra
and BOOT interpreter layers are shared ancestry with OpenAxiom and are
largely host independent once translated; the real work is the host
layer and the build.

- *Stage 0 --- Build the oracle.* Build OpenAxiom on the
  target platform to obtain a working reference system. /Done/;
  evidence in Section~[[#sec:oracle][sec:oracle]] and Section~[[#sec:gotchas][sec:gotchas]].
- *Stage 1 --- Map the bootstrap.* Document the
  =bootsys=/=interpsys=/=AXIOMsys= chain and every
  host-Lisp touch point. This chapter (Section~4) is that map.
- *Stage 2 --- Host abstraction.* \emph{Done, and smaller
  than expected.} Inspecting =books/bookvol5.pamphlet= revealed
  that daly's leaf host covers are /already/ conditionalised for
  SBCL: =getenviron= carries \texttt{#+sbcl (sb-ext:posix-getenv
  var)} and =reclaim= carries =#+sbcl (sb-ext::gc)=. The
  one architecturally central cover that lacked an SBCL arm was
  =spad-save=, the image dump itself. We added it in place,
  prose first: an =#+:sbcl= branch calling
  =sb-ext:save-lisp-and-die= with =:executable~t= and,
  when =boot::restart= is bound, =:toplevel=. Because the
  covers already live in the books and only needed extending, no new
  =portability.lisp.pamphlet= and certainly no OpenAxiom-style
  =src/lisp/= directory were created --- the host abstraction is
  extended exactly where daly already kept it. The lesson recorded for
  later stages: daly is more SBCL-ready at the leaf than at the
  architecture; the gaps are the image dump (now closed), the foreign
  interface, and the bootstrap internals.
- *Stage 3 --- Foreign interface.* \emph{Cfuns done and
  verified; sockets deferred.} The 23 =defentry= bindings split
  sharply. Five are not really foreign: in =cfuns.lisp.pamphlet=
  GCL supplied =hashString= and =hashCombine= as C compiled
  into its image with =Clines= (which SBCL has no analogue for),
  and =directoryp=/=writeablep= are filesystem predicates;
  each is trivial. We reimplemented all four in pure Common Lisp under
  =#+:sbcl=, removing the foreign call entirely, and verified the
  two hashes /bit-for-bit/ against the original C across empty,
  single-character, and type-name inputs and the $2^{24}$ boundary. The
  remaining seventeen live in =sockio.lisp.pamphlet= and split
  again: three (=plus\_infinity=, =minus\_infinity=,
  =NANQ=) are IEEE double values the =Float= domain needs,
  reimplemented in Lisp and verified under SBCL to yield $+\infty$,
  $-\infty$ and a quiet NaN; the other twelve are the genuine HyperDoc
  client/server sockets, which we =#+:sbcl=-stub so an accidental
  call raises a clear message (the console =AXIOMsys= never calls
  them, since =\$SpadServer= is nil) and which become real
  =sb-alien= routines if and when HyperDoc is built. So of the 23
  bindings, eight are now pure Lisp, three are pure-Lisp float constants,
  and twelve are deferred socket stubs --- =sb-alien= is reserved
  for exactly the irreducibly foreign socket layer and nothing else. The
  rule the files now record: reimplement trivial C in Lisp; reserve
  =sb-alien= for the irreducibly foreign.
- *Stage 4 --- Drop bundled GCL.* \emph{Analysed; see
  Section~[[#sec:stage4][sec:stage4]].} Point =bin/lisp= at system SBCL and
  delete the =lspdir= GCL build. The investigation showed this
  cannot be completed independently of Stage 5: the depsys recipe that
  selects the host also calls GCL-only =compiler::= internals, so
  the two stages are one combined effort.
- *Stage 5 --- Bootstrap on SBCL.* \emph{Path found; see
  Section~[[#sec:stage5][sec:stage5]].} Make the BOOT translator and the residual
  =si::=/=compiler::= calls work under SBCL until
  =AXIOMsys= dumps. The depsys recipe is a /reversion/ to its
  documented simple load-then-save form rather than an invention --- the
  GCL =compiler::link= path exists only to work around a
  limitation SBCL does not share. What remains is iterative build-debug
  against the oracle (the =makedep.lisp= file list and the BOOT
  translator on SBCL). This combined Stage~4/5 rewire is the project's
  long pole.
- *Stage 6 --- Compile the algebra.* With the interpreter
  alive, compile the SPAD library and confirm basic domains compute.


\section{Stage 4 in detail: replacing the GCL host}
# label: sec:stage4

Stage 4 is where the port stops being local edits to cover functions and
becomes surgery on the build itself. Investigating the literate
Makefiles produced both the substitution plan and an honest surprise:
Stage 4 cannot be finished without Stage 5, because the same recipe that
selects the host Lisp also calls GCL-only compiler internals.

\subsection{How the GCL host is built and used}

The top =Makefile= (tangled from =books/Makefile.pamphlet=)
carries the whole GCL apparatus. =GCLVERSION=gcl-2.6.13pre= and
=GCLDIR:=\$\{LSP\}/\$\{GCLVERSION\}= name a GCL to build from the
sources in =zips/=; the =lspdir= target compiles it
(=cd lsp ; make gcldir=) and then copies the result,
=\$\{GCLDIR\}/unixport/saved\_gcl=, into the build's =bin=.
That saved GCL image /is/ the host Lisp. Everywhere downstream it is
referred to as =bin/lisp=: in =src/interp/Makefile= both
=LISPSYS= and =LISPTANGLE= are =\$\{OBJ\}/\$\{SYS\}/bin/lisp=,
so the same GCL image both tangles the literate sources and hosts the
compile.

\subsection{How the bootstrap drives that host}

The three images are produced by piping a save form into that Lisp. The
=save depsys image= chunk of =src/interp/Makefile.pamphlet=
does, in essence,

\begin{verbatim}
  echo '... (spad-save "${DEPSYS}")' | ${LISPSYS}
\end{verbatim}

\noindent and =interpsys= and =AXIOMsys= are saved the same
way. This is the join with Stage~2: the =(spad-save ...)= that the
Makefile pipes in is exactly the cover whose =#+:sbcl= arm we
added. Once =bin/lisp= is SBCL, that arm fires and
=save-lisp-and-die= writes the image. The cover side is ready.

\subsection{The substitution, and why it is gated on Stage 5}

The intended change is small to state: make =bin/lisp= resolve to
the system =sbcl= (or a one-line wrapper), and skip the
=lspdir= GCL build entirely --- the =zips/= GCL sources and
their patches then become dead weight to be removed. Stated that simply,
it sounds like a Stage 4 one-liner.

It is not, because the depsys recipe does more than pick a Lisp. The same
chunk calls =compiler::make-proclaims=, =compiler::link= and
=compiler::emit-fn= --- GCL compiler internals with no SBCL
equivalent. The moment =bin/lisp= becomes SBCL, those calls fail.
So pointing the build at SBCL and rewriting the depsys recipe to use
SBCL's compilation model are the /same/ task; they cannot be
sequenced apart. Stage 4 (choose the host) and Stage 5 (make the
bootstrap run on that host) are therefore one combined effort, driven
iteratively against the OpenAxiom oracle: change a recipe, run it under
SBCL, compare the failure to how OpenAxiom's corresponding Makefile and
=depsys= equivalent solved it, repeat. This is the long pole of
the whole project, and it is the next body of work.

\section{Stage 5: rewriting the depsys bootstrap for SBCL}
# label: sec:stage5

Reading the =save depsys image= recipe in
=src/interp/Makefile.pamphlet= turned the combined Stage~4/5
problem from daunting into tractable, because the recipe documents its
own history.

\subsection{What the active recipe actually is (a correction)}

A first reading of this file is misleading, and the correction matters
enough to record. The prose around the save step shows an elaborate
GCL procedure --- =si::*collect-binary-modules*= to record every
compiled =.o= module, =compiler::link= as a Lisp interface
to the C =ld= linker, =compiler::emit-fn=, SGC --- and a
casual reader (this author included, at first) concludes the live recipe
statically links object modules through =ld=.

It does not. Mapping every =\begin{chunk}= and =\begin{verbatim}=
marker in the section shows that the elaborate procedure lives entirely
in =\begin{verbatim}= blocks with /no/ surrounding
=\begin{chunk}=; it is documentation of an approach, not tangled
code. There is exactly one chunk named =save depsys image=, and it
is the simple form:

\begin{verbatim}
  (progn (load "${OUT}/makedep.lisp")
         (spad-save "${DEPSYS}"))
\end{verbatim}

\noindent The =\getchunk{save depsys image}= in the =depsys=
target therefore tangles /this/, not the =ld= procedure. The
active depsys save has been the simple load-then-save all along; the
=compiler::link= narrative is dead prose. The lesson, and the
reason this subsection exists: in a literate file, what tangles is the
=\begin{chunk}=, never the surrounding prose, however authoritative
the prose sounds.

\subsection{Why this makes SBCL close}

The simple form is almost host-neutral. =load= and the
=compile-file= forms that build =makedep.lisp= are standard
Common Lisp, and the =#+:sbcl= arm added in Stage~2 turns the
=spad-save= into =save-lisp-and-die=. We validated the
whole cycle in miniature: piping
=(progn (load "makedep.lisp") (spad-save "depsys-img"))= into a
clean SBCL produced a 36~MB standalone executable that, run, booted into
the =boot::restart= top level and exited cleanly. The mechanism
works; only the build's host-specific variables stand between it and the
real depsys.

\subsection{The genuine GCL remnants, and what stays open}

Three host-specific pieces remain in the depsys path, far fewer than the
=ld= narrative suggested. =\$\{O\}= is the compiled-object
extension, =o= for GCL and =fasl= for SBCL.
=\$\{LISPSYS\}= is =bin/lisp=, which must become a clean
SBCL --- the spike showed =save-lisp-and-die= demands a
single-threaded image, so the wrapper must pass
=-{}-no-userinit -{}-no-sysinit= or any thread-starting init (a
SLYNK in =.sbclrc=) aborts the save. =\$\{PROCLAIMS\}= is
generated by =compiler::make-proclaims= and is the one genuinely
GCL-only form in the makedep sequence; on SBCL it must be emptied or
regenerated by other means. Beyond depsys, the BOOT translator and the
earlier tangle/compile chain must also run under SBCL. These are found
the same way: change a variable, build under SBCL, compare the failure to
OpenAxiom, repeat. The destination is now known; the iteration is the
long pole.

\subsection{The first cut, taken and verified}

The first two of those three remnants are now closed. The top
=Makefile.pamphlet= gained a =LISPFLAVOR= selector
(default =gcl=, so every existing platform is untouched); under
=make LISPFLAVOR=sbcl= the object extension =O= becomes
=fasl= and the =lspdir= target, instead of compiling the
bundled GCL, writes a two-line wrapper installing the system SBCL as
=bin/lisp= with the init files excluded. Three verifications
gate the change. The tangled =Makefile= was diffed against the
tracked one: the only changed lines are the intended ones, and the
tracked file had first been proven byte-identical to the root chunk, so
the literate pipeline itself is sound. The default flavor's dry run
still builds GCL. And =make lspdir LISPFLAVOR=sbcl=, run for
real, wrote the wrapper and a piped form answered
=host=SBCL 2.6.3= through it. One sequencing note for later
readers: =lspdir='s prerequisite tangles
=lsp/Makefile.pamphlet= /and/ typesets its documentation,
so =rootdirs= and =axiom.sty= must have run first ---
invoking =lspdir= in isolation fails in LaTeX, not in Lisp.
What remains open is unchanged: =\$\{PROCLAIMS\}= and the
depsys/BOOT chain itself, which the next iteration drives by running
=make LISPFLAVOR=sbcl= onward into =src/interp=.

\section{Build gotchas observed on macOS}
# label: sec:gotchas

Building the oracle on Apple Silicon surfaced three traps that will
recur when Axiom itself is built on this platform. They are recorded
here so the lesson is not lost.

\subsection{Use the Apple C compiler, not Homebrew's clang}

A Homebrew =clang= earlier in =PATH= cannot link
executables, failing with =ld: library 'System' not found=,
because it does not default to the macOS SDK sysroot. The build must be
told to use Apple's compiler, =CC=/usr/bin/clang=. Axiom's own
C pieces (=src/lib=, =clef=, the graphics drivers) will
need the same.

\subsection{HyperDoc is a hard dependency and needs X11}

One cannot simply skip the HyperDoc help browser: in the build graph the
interpreter image depends on HyperDoc preprocessing
(=all-interpsys= depends on =all-hyper-pre=). HyperDoc's C
sources include X11 headers unconditionally, so X11 is required even for
a non-graphical build. macOS does ship X11 via XQuartz under
=/opt/X11=, but =autoconf= does not search there by
default; the location must be supplied explicitly
(=-{}-x-includes=/opt/X11/include -{}-x-libraries=/opt/X11/lib=).
For Axiom, the same applies, or HyperDoc must be stubbed wholesale in
Stage~3.

\subsection{Drive AXIOMsys directly for non-interactive checks}

The =open-axiom= launcher starts a session manager (=sman=)
that expects a real terminal; feeding it a command file through a pipe
hangs. For scripted verification, run the raw =AXIOMsys= image
with the system directory exported and the commands on standard input.
Axiom's =sman= behaves the same way.

\section{Status: the port runs}

All stages are complete. =depsys=, =interpsys= and
=AXIOMsys= build and save under SBCL on Apple Silicon; the full
algebra compiles (1212 NRLIBs); the interpreter computes end to end ---
=1+1=, =factor=, =integrate=, matrices, series,
=solve=, =gcd= of large integers, partial fractions, and
the rest all return correct results.

\subsection{Regression result}

Of the 525 runnable =src/input= regression tests (the graphics
SKIP set excluded), *519 run without a Lisp error* (98.9\%).
Every failure was a GCL-vs-ANSI divergence; the classes fixed, each
cross-checked against fricas/open-axiom, were:

- *uninitialised vectors* --- GCL's =GETREFV= fills
  NIL, SBCL's =make-array= fills 0; the 0 in an add-chain slot
  built a self-referencing domain (infinite method lookup). Added
  =:initial-element nil= (open-axiom =newShell=).
- *lenient car/cdr* --- BOOT's =is= pattern was
  hand-compiled to raw =(car x)= that crashes on an atom on
  SBCL. Restored with daly's own =eqcar=/=ifcar=/%
  =ifcdr= safe-accessor macros.
- *CLtL1 funcallable lambda-lists* --- \texttt{(funcall
  '(lambda ...) x)} needs =COERCE ... 'FUNCTION= on SBCL.
- *(character n)* on an integer, *(string pathname)*,
  *(probe-file symbol)*, *(namestring nil)*,
  *open(:output) on a directory*, *(pathname-type nil)*
  --- ANSI rejects designators GCL accepted; coerced or guarded each.
- *unbound specials* (=\$indexList=,
  =getMsgFTTag=) --- =defvar= to nil.
- *printing self-referential domain vectors* ---
  =*print-circle* t=.
- *improper-list display message*, \textbf{nil output
  stream}, *latin-1 pamphlet decoding in the tangler*.


\subsection{The remaining six: not portable here}

The last six are not SBCL-port defects and cannot pass in a headless
SBCL tree:

- =graphviz= --- shells out to the =dot= binary.
- =herm= --- =)library herm= loads a prebuilt
  library file absent from the tree.
- =monitortest=, =newtonlisp= --- load external files
  (e.g. =funcall.o=) the test never builds.
- =unittest2= --- reads a chain of GCL compiler internals
  (=compiler::*compile-verbose*=,
  =*suppress-compiler-notes*=, ...) whose expected output is
  GCL's own values.
- =unittest4= --- =)lisp (trace ...)= then prints
  domain-vector arguments; SBCL's tracer recurses on the deep
  structure.


The socket layer is stubbed (no-op) rather than built, so =draw=
returns a viewport object without a live viewport manager; wiring the
real HyperDoc/graphics server (as fricas/open-axiom do) is the one
genuine piece of follow-up work.
